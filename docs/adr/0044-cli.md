# 0044 — The CLI signs in with a device code, plans uploads it detects from git, and prints the server's timeline

**Status:** Accepted, 2026-11-14.

## Context

Phase 20 adds a command-line client: `stackwright login`, `plan`, `runs`
and `logs --follow`. A plan from the CLI uploads the working tree and
never applies. Its timeline must be the same as the web app's.

Before phase 20, the Connect API accepted only a browser session, a
cookie with a CSRF header. The `swt_` tokens are for the state backend
only, and the `swj_` tokens are for jobs. The web app wrote the timeline
text itself, in TypeScript.

## Decision

**Sign-in is the OAuth device flow (RFC 8628).** `stackwright login`
asks the server for a device code. It prints a short user code and a
URL, `/device`, and polls. The user opens the URL in a browser where
they are signed in, checks that the code and the machine name match, and
approves. The next poll gets a CLI token, once. A device code ends after
10 minutes, and a poll faster than the interval gets `slow_down`.

**A CLI token acts as its user.** The user chose this: a CLI token has
the same roles as the user's browser session, in every org. It starts
with `swc_` and goes in the `Authorization` header. The server keeps
only its SHA-256. It ends after 30 days without use, and the user can
revoke it in the web app. The CLI keeps it in
`~/.config/stackwright/config.json`, mode 0600, or reads
`STACKWRIGHT_TOKEN`.

**A plan from the CLI is speculative.** `CreateRun` with `speculative`
set needs an upload, makes a plan-only run with trigger `cli`, and is
allowed on a project that a repository is linked to. The database
refuses a `cli` run that is not plan-only, so no code path can apply
it.

**The CLI finds the project from git.** It reads the git remote and the
folder's path in the repository, and finds the project that is linked
to that repository at that path. `--org`, `--project` and `--workspace`
override what it finds. With several workspaces and no flag, it asks on
a terminal and fails otherwise. It uploads the files that git tracks,
and the untracked files that `.gitignore` does not exclude, from the
repository's root, so `../modules` resolve as in a pushed commit.

**The server writes the timeline text.** Each run event carries `text`,
`tone`, `detail` and `fix`, which Go writes from the event's type and
payload. The web app and the CLI print them, so the two timelines are
the same by construction. Times are in UTC.

**The server serves the CLI.** The image holds the `stackwright` binary
for macOS and Linux, on arm64 and amd64, gzipped, with their SHA-256
sums. The web app's CLI page links them. The server sends the gzipped
file to a client that accepts gzip, and unpacks it for one that does
not.

## Alternatives

- **A browser redirect to localhost.** One click, but it fails over SSH
  and in containers.
- **A token pasted from Settings.** No new flow, but tokens get copied
  around.
- **A read-and-plan token.** Safer if a laptop is lost, but the user
  wanted the CLI to do what they can do.
- **A `.stackwright` file in the folder.** Simple, but one more file to
  commit or to ignore.
- **Port the timeline to Go next to the TypeScript one, with a shared
  test file.** Two copies that a test keeps equal, where one copy cannot
  drift.

## Consequences

- A lost laptop with a CLI token can approve applies, as its user can.
  Revoking the token in the web app stops it.
- The image grows by about 44 MB, the four gzipped binaries.
- The CLI's plan of a linked project uses the local files, not the
  pushed commit. Its run says it came from the CLI.
